# SDG2410J 课程大项目讲解：个人碳足迹计算器

这份说明根据课程项目材料整理，用来回答一件事：这个 project 到底要做什么、做到哪一步、哪些数字不能改、哪些决定要小组自己做。

## 1. 一句话说明

小组要为一名**虚拟的上海交通大学学生李明**做一份**探索性的个人碳足迹计算器**：一个能在浏览器里打开的交互网页。它接收活动数据，用二氧化碳当量（CO₂e）估算排放，解释结果，并给出和这些活动相关的减排建议。

这不是交一份最终正确的碳排放报告。课程要你们先把设计意图写成提示词，用生成式 AI 做出第一版可运行原型，再随着碳核算知识增加，不断改边界、归因、数据和算法，并且能讲清楚每一次选择为什么这样定。

课程大纲把这件事写成学习目标第 6 条：小组协作、用生成式 AI 支持，设计并迭代改进一个探索性个人碳足迹计算器；每个人还要能单独说明它的核算边界、排放归因逻辑、数据来源、假设、计算步骤、主要修改和局限。课程项目占成绩 **40%**。

## 2. 它在这门课里处在什么位置

课程是上海交通大学密西根学院（Global College）2026 年秋季的 **SDG2410J Carbon Accounting / 碳核算**，授课教师 Haishan Yu，授课语言英语，32 学时、2 学分，面向工程本科生，无先修课。

课的主线不是“做一个 App”，而是同一套分析框架在不同尺度上怎么用：

| 分析问题 | 在这个项目里对应什么 |
| --- | --- |
| 核算目的 | 估算李明个人活动对应的温室气体排放，并据此讨论减排 |
| 分析单元 | 一个人：虚拟学生李明 |
| 核算边界 | 哪些活动算进足迹、时间范围是一周 / 一学期 / 一年 |
| 排放归因 | 宿舍合用电怎么分到他头上，网约车只有他一个人时怎么算 |
| 数据 | 活动量用画像里的共享事实；排放因子要小组另找并写明来源 |
| 方法 | 最基本的是「活动数据 × 排放因子」，汇总成 CO₂e |

课上会依次讲国家清单、城市清单、组织清单、产品碳足迹、项目/政策评估、融资排放，以及报告与披露。个人计算器是贯穿全课的练习场：Lecture 15 是 Project Studio 展示，Lecture 16 是期末考试。

所以计算器既是软件作业，也是核算作业。界面能打开只满足早期里程碑；后面会被追问：这个数代表什么、边界包了什么、没包什么、假设有没有被说成事实、同一个活动有没有算了两次。

## 3. 项目要交的东西，分两层看

### 3.1 早期就要交出来的（Milestone 1，2026-09-24 16:00 前）

这三步都是 0 分的过程作业，但是后面迭代的起点，必须保留。

**Milestone 1a — Prompt V1**

- 用思维导图和 CO-STAR 工作表，**小组自己写**第一版提示词。
- 明确要求：**不要用 AI 写这一版。**
- 提交：组号、成员姓名、Prompt V1 全文。
- 文件名：`Group##_PromptV1`。
- 由一名成员代表全组提交。

**Milestone 1b — Prompt V2**

- 用一个 AI 工具改进 Prompt V1 的清晰度、结构和完整度。
- 小组必须审阅 AI 的建议，决定保留、修改或拒绝。
- Prompt V2 必须仍然符合小组自己的设计意图，不能直接交 AI 第一次返回的稿。
- 提交：组号、成员姓名、所用 AI 工具名称、小组批准后的 Prompt V2 全文。
- 不要在这一步交计算器，也不要交 AI 的解释。
- 文件名：`Group##_PromptV2`。

**Milestone 1c — Prototype 0**

- 把小组批准的 Prompt V2 输入选定的 AI 对话工具，生成计算器的第一版可运行代码。
- 保存为**单个 HTML 文件**（里面包含所需的 HTML、CSS、JavaScript）。
- 提交前至少满足：
  - 能在浏览器里当网页打开；
  - 能看到计算器界面；
  - 用户能输入信息或做选择；
  - 至少能产出一个结果或反馈；
  - 扩展名是 `.html`，不是 `.txt`。
- 文件名：`Group##_Prototype0.html`。
- 不要用截图、AI 对话链接或 Word 代替 HTML。
- 作业说明写明：Prototype 0 是起点，不要求精致，也不要求完全正确。请保留这一版，后面边学边测、边评、边改。

### 3.2 整个学期真正要做成的

大纲要求的完整能力比 Prototype 0 高一层。做到后期，小组和每个成员应能说明：

1. 核算边界：算了哪些排放，故意不算哪些，时间范围是什么。
2. 归因逻辑：合用的电、合住的宿舍、已经包含在 21 餐里的外卖，分别怎么归到李明。
3. 数据来源：活动数据哪些来自共享画像，排放因子来自哪里。
4. 假设：画像没给的信息，小组补了什么，为什么需要它。
5. 计算过程：活动数据如何换成 CO₂e，各类如何加总。
6. 主要修改：相对 Prototype 0 改了什么、为什么改。
7. 局限：结果不能支持什么结论。

## 4. CO-STAR 工作表在项目里干什么

CO-STAR 不是计算器的功能清单，而是**把设计简报写成给 AI 的提示词**的表格。页脚注明框架改编自 Sheila Teo 的提示词方法。工作表标题是 *From Design Brief to a Prompt*。

使用方式写在表头：先用思维导图记下小组想传达给 AI 的选择；关键词和短句就够；**这一步还不要用 AI。**

六个字母里，有的内容是课程已经写死的，有的必须小组自己选。

### C — Context（背景）

告诉 AI 它在帮谁做什么。

课程给定的说法是：你们是正在完成碳核算课程项目的本科生小组，要为一个**虚拟的交大学生**开发个人碳足迹计算器。

### O — Objective（目标）

告诉 AI 具体要做出什么。课程给定的功能是四个，缺一不可：

1. **交互式网页计算器**；
2. **接收活动数据**；
3. **用 CO₂e 估算排放**，并把结果展示出来、解释清楚；
4. **给出与这些活动相关的减排建议。**

CO₂e（二氧化碳当量）是把不同温室气体按增温能力折成二氧化碳的统一单位。计算器报的是这个单位，不是只报二氧化碳。

### S — Style（样式）

工具看起来、用起来是什么感觉。这部分**由小组选**，建议只定两到三个具体偏好，不要堆形容词。工作表给的例子：干净简单、卡片式、仪表盘式、分区清楚、分步填写、结果可视化、适配手机。

### T — Tone（语气）

计算器怎么跟用户说话。作用范围包括：问题怎么问、结果怎么解释、减排建议怎么写。小组要选一种，例如中性、友好、鼓励、简洁，或其他你们能说清楚的语气。

### A — Audience（对象）

告诉 AI 谁会用这个计算器，以及这个用户的哪些特点会影响输入项、功能、语言或界面。

起点必须是共享画像里的李明。小组可以补充特点，但有两个限制：

- 只补充**会影响输入、功能、语言或界面**的特点；
- 每一条补充都要标明这是**小组假设**，不能写成画像里的事实。

### R — Response（返回形式）

规定 AI 必须交回什么、屏幕上怎么组织。课程写死的交付物是：

> 一个完整的 HTML 文件，内含所需 HTML、CSS 和 JavaScript，保存后能直接在浏览器打开。

小组还要列出界面上必须出现的区块。工作表建议可以考虑：

- 活动输入区
- 计算按钮和重置按钮
- 总排放
- 分类排放
- 简短解释
- 减排建议

这些是“可以考虑纳入”的例子，不是另一份隐藏评分表。小组应在提示词里写成明确清单，避免 AI 自己省略结果解释或减排建议。

## 5. 虚拟学生李明：全班共用的核算对象

材料标题是 *Shared Virtual SJTU Student*。副标题说明两件事：这是**每个小组的共同起点**；这是一个**说得通的课程案例**，不是对全体交大学生的统计描述。

### 5.1 身份与生活场景

| 项目 | 共享事实 |
| --- | --- |
| 姓名 | 李明（Li Ming） |
| 年龄 | 20 岁 |
| 年级与专业 | 二年级，工科 |
| 居住 | 四人宿舍 |
| 日常范围 | 主要在校园内 |
| 出行节奏 | 偶尔离校，或回家探望家人 |
| 数据特点 | 各类活动的时间单位不一样 |

最后一条会直接决定程序怎么写。画像里同时出现“每周”“每月”“最近 30 天”“每教学学期”。如果结果要可比，计算器必须选一个统一的报告周期（例如每周、每学期或每年），并把其他单位换算过去。**一学期有多少周，画像没有给**，一旦你们要换算，这就是小组假设，必须标明。

### 5.2 六类活动

下面“共享事实”一列的数字不能改。纳入计算器的类别可以少于六类，但只要纳入，数值就用这些。

#### 出行（校园和市内）

| 活动 | 共享事实 |
| --- | --- |
| 校园内步行或骑行 | 约 20 km / 周 |
| 地铁 | 每周 2 次单程，每次 15 km |
| 网约车 | 每月 2 次单程，每次 10 km，通常独自乘坐 |

由此可以直接算出的活动量：

- 地铁：2 × 15 = **30 km / 周**
- 网约车：2 × 10 = **20 km / 月**

画像没有给：具体地铁线路、车型、网约车能源类型（油车 / 电车）、步行和骑行的比例。步行和骑行的使用阶段排放通常接近零，但“算进来并显示为零”和“边界里根本不包含”是两种不同做法，小组要说清楚用的是哪一种。网约车写明通常独自乘坐，因此不要再按多名乘客分摊；如果界面允许用户改乘坐人数，默认值应为 1 人。

#### 饮食

21 顿正餐 / 周，构成已经配平：

| 类型 | 每周顿数 |
| --- | --- |
| 牛肉或羊肉 | 3 |
| 其他肉类 | 8 |
| 鱼、蛋、奶或大豆 | 5 |
| 以植物为主 | 5 |
| 合计 | 21 |

另外两条事实：

- 大多数饭在校园食堂吃。
- **每周 2 顿外卖已经包含在这 21 顿里。**

第二点是防重复计算的关键。外卖不是第 22、23 顿。食物本身的排放已经在 21 顿的分类里。若小组认为外卖还有包装或配送排放，那是在食物排放之外另加的一部分，而且包装重量、配送距离画像都没有给，必须标成假设。不要把 2 顿外卖再按某一类食物加一遍。

“其他肉类”和“鱼、蛋、奶或大豆”是合并类。猪肉、鸡肉、鸡蛋、牛奶的排放因子差很多。若计算器拆得更细，拆分比例是小组假设。

#### 宿舍与能源

| 项目 | 共享事实 | 明确没给的信息 |
| --- | --- | --- |
| 居住人数 | 4 人一间 | — |
| 房间用电 | 最近 30 天 **120 kWh**，而且是**整间房** | 没有按人分好 |
| 热水澡 | 每周 6 次，每次约 8 分钟 | **热水的能源种类和用量都没有** |

用电不能把 120 kWh 直接当成李明一个人的用量。四人分摊是合理的默认处理，但“平均分成 4 份”本身是归因规则：30 kWh / 人 / 30 天。如果有人几乎不在宿舍、或某台电器主要归一个人用，平均分摊就会偏离，小组若仍用平均分摊，要写成假设。

另外，30 天不等于一个日历月。和“每月”的网约车、快递放在一起时，不要默默当成同一个分母。

洗澡：每周 6 × 8 分钟 = 48 分钟热水。没有能源种类（电热水器、燃气、校园集中热水）和流量，就不能把某一度电或某一立方米燃气写成事实。要算这一项，必须补充假设并解释为什么需要它；不打算引入无法核实的能源数据时，也可以不把洗澡单独算进排放，但要在边界说明里写明排除原因。

#### 商品与快递

| 项目 | 共享事实 | 明确没给的信息 |
| --- | --- | --- |
| 网购 | 3 个包裹 / 月 | 材质、价格、包装重量、产品寿命都没有 |
| 衣物 | 每教学学期 2 件 | 同上 |

没有重量、材质或价格，就做不出像样的产品碳足迹。小组只有几条路，而且都要讲清楚：

- 用一个“每个包裹”或“每件衣服”的通用排放因子，并标明这是假设；
- 先假设价格，再使用基于消费金额的因子，价格假设必须单独标明；
- 这一类先不纳入计算器，在边界里说明：共享事实只有件数，没有做产品碳足迹所需的物料数据。

衣物还有时间问题。一件衣服的生产排放发生在购买时，但使用可以跨多个学期。是把生产排放全部算进购买的那个学期，还是按使用寿命分摊，这是方法选择，不是画像里的事实。

#### 城际出行

| 项目 | 共享事实 |
| --- | --- |
| 回家 | 每教学学期 2 次往返，交通方式为高铁 |
| 距离 | 单程约 220 km |

一次往返是 220 × 2 = 440 km，一学期两次往返合计 **880 km 高铁**。这项和校园步行、地铁、网约车是不同的活动，不要并进“每周出行公里数”后用同一个排放因子。

#### 废弃物与回收

| 项目 | 共享事实 | 明确没给的信息 |
| --- | --- | --- |
| 宿舍一般垃圾 | 约 3 个小袋 / 周 | **没有质量，也没有处理路径** |
| 可回收瓶或罐 | 约 3 个 / 周 | 同上 |

“小袋”不能直接乘排放因子。若要计算，必须假设每袋大约多少千克，并假设去向是填埋、焚烧还是其他。处理路径对结果影响很大，不能把某一种写成已知事实。

用电那一行写明了“整间房”。垃圾这行只写“宿舍一般垃圾，每周约 3 个小袋”，**没有写这是四人合计还是李明本人**。不要自行把它除以 4，除非小组把“这是全屋垃圾”标成假设。瓶子是否已经包含在那 3 个小袋里，画像也没说；若两边都算，可能重复计算同一批废弃物。

## 6. 使用共享事实的四条规则

画像最后一节 *How to use the shared facts* 是项目的硬约束。

1. **共享数值保持不变。** 计算器不必覆盖每一项活动，但用到的项必须沿用画像里的数字。
2. **缺失信息不能写成已核实的事实。** 热水能源、垃圾质量、衣服材质、学期周数，都属此类。
3. **小组补充的每一条假设都要标注，并说明为什么需要它。** 需要它，通常是因为没有这条假设就无法完成某一步换算或选择排放因子。
4. **同一项底层活动不要算两次。** 已经点名的风险是：2 顿外卖已在 21 顿正餐内。同类风险还有：房间总电量与个人分摊、一般垃圾与其中的瓶子、食堂用餐与宿舍用电（食堂加工能耗通常不在宿舍电表里）。

这四条会决定界面上怎么呈现结果。比较稳妥的做法是：默认值预填李明的共享事实；用户可以改输入来做情景比较；凡是默认值来自假设而不是画像，界面或说明里就标出来。

## 7. 计算器建议具备的结构

把工作表的 Objective、Response 和画像放在一起，第一版之后的计算器可以按这个结构理解。Prototype 0 只要“能打开、能输入、能出一个结果”；下面是课程材料隐含的完整形态。

### 输入

按画像的类别组织，时间单位跟原始数据一致，避免用户不知道该填“每周”还是“每月”：

- 出行：步行/骑行公里（周）、地铁次数与单程距离（周）、网约车次数与单程距离（月）、是否独自乘坐
- 饮食：各类正餐顿数（周），并提示外卖已包含在总顿数中
- 宿舍能源：房间用电（最近 30 天）和分摊人数；洗澡次数与时长（若纳入）
- 商品：包裹数（月）、衣物件数（学期）
- 城际：高铁往返次数（学期）和单程距离
- 废弃物：垃圾袋数（周）、可回收瓶罐数（周）

默认数字用第 5 节的共享事实。不纳入的类别就不要在界面上假装已经计算。

### 计算

对每个纳入的活动：

`排放（kg CO₂e）= 活动数据 × 排放因子`

然后按报告周期换算，再按类别加总，得到总排放。排放因子**不在这两份项目材料里**。Prototype 0 可以先用占位因子把计算跑通，但占位因子不能长期当作课程结论。后期必须写明因子来源，并在结果解释里区分“活动数据来自共享画像”和“因子来自某文献、数据库或课堂材料”。

### 输出

工作表点名的结果形式：

- 总排放（写明周期：每周 / 每学期 / 每年）
- 分类构成
- 简短解释：这个数是怎么来的，边界包含什么
- 减排建议：必须和李明实际有的活动有关，例如正餐结构、地铁与网约车、快递频次，而不是一套与输入无关的通用口号

重置按钮用于回到李明的默认画像，方便和用户改过的情景比较。

### 解释层（后期会变得比界面更重要）

结果旁边或单独的说明里，建议固定回答这几个问题：

- 报告周期是什么，不同时间单位怎么换过来的？
- 120 kWh 怎么归到李明一个人？
- 哪些活动用了假设？假设是什么？
- 哪些活动故意没算？为什么？
- 哪些建议只是情景比较，不是把“如果他改变行为，全世界因此少排的量”当成已经发生的事实？

最后一点对应课堂里归因核算（attributional）和后果核算（consequential）的区别。个人足迹计算器的主结果是：这些排放如何归到李明已发生的活动上。减排建议是在问“如果活动数据变了，足迹数字会怎样”，应标明它是情景，不要和主结果混成一个数。

---

## 8. 小组还要自己做的决定

这些决定写进思维导图、CO-STAR 和 Prompt V1，不要等 AI 替小组选。

| 决定 | 为什么它会影响程序和核算 |
| --- | --- |
| 纳入哪几类活动 | 画像允许不覆盖全部六类；每少一类，边界说明里就要有排除理由 |
| 统一的报告周期 | 周、月、30 天、学期混在一起，不统一就无法相加 |
| 一学期按多少周 | 画像没给，换算必用假设 |
| 宿舍电如何分摊 | 120 kWh 是整间房 |
| 洗澡算不算、按什么能源算 | 只有时长，没有能源 |
| 垃圾按什么质量、什么处理路径 | 只有“小袋”和个数 |
| 衣服和包裹用什么因子 | 没有材质、重量、价格、寿命 |
| 外卖是否另计包装或配送 | 食物本身不能再算一次 |
| 视觉风格两到三个 | Style，写进提示词 |
| 语气 | Tone，决定文案而不是算法 |
| 界面区块清单 | Response，决定 AI 生成的页面结构 |
| 补充的用户特征 | 只能加影响输入、功能、语言或界面的点，并标为假设 |

Prompt V1 建议就按 C → O → S → T → A → R 写。Context 和 Objective 用课程给定的任务，不要改成另一个产品。Audience 里先复述李明的共享事实，再单列“小组假设”。Response 里写死：只返回一个可保存、可打开的 HTML 文件，并列出必须出现的界面区块。

## 9. 容易做错的地方

1. **用 AI 写 Prompt V1。** 1a 明确禁止。AI 用在 1b 改提示词、1c 生成代码。
2. **把 Prototype 0 当成终稿。** 作业要求保留初版，后面用课程里的边界、因子和归因去改它。
3. **改动共享数字。** 例如把地铁改成每周 5 次，或把 21 顿改成别的结构，就不再是共同案例。用户可以在计算器里改输入做情景，默认案例必须仍是李明。
4. **把没提供的信息写成事实。** 典型的是虚构热水器功率、每袋垃圾 2 kg、衣服是纯棉、学期正好 16 周，却不标注假设。
5. **重复计算。** 21 顿之外再加 2 顿外卖；120 kWh 既按房间算一遍又按个人算一遍；瓶子既算进垃圾又单独算一次。
6. **时间单位直接相加。** 把“每周千克”和“每学期千克”加成一个没有周期的总数。
7. **减排建议和输入脱节。** 建议应指向他真实的高排放活动。牛肉/羊肉每周 3 顿、网约车、快递，通常比步行更值得讨论；具体高低要等排放因子算完才能下结论。
8. **1b 把 AI 的说明或代码一起交上去。** 1b 只交小组批准的提示词。1c 只交 HTML。

## 10. 和后续写代码的关系

仓库目前是课程材料，计算器本身要从 Prototype 0 开始产生。材料已经把技术形态定死了：**单个 HTML 文件，浏览器直接打开，不依赖安装步骤。** 第一版可以由 AI 根据 Prompt V2 生成；之后的修改应当让核算逻辑变得可读，例如：

- 共享事实、小组假设、排放因子分开存放，界面上能看出哪一类是哪一种；
- 每个类别的活动数据、时间换算、排放因子、CO₂e 结果能对上；
- 总排放等于各类之和，重置能回到李明的默认值；
- 解释文字随结果变化，而不是一段固定说明。

做到这一步，软件结构就和课程要求的“能解释边界、归因、数据、假设、算法和局限”是同一件事。
